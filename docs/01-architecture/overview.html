系统总览

本地优先、聊天式的求职简历工作台：把 JD 粘进一个对话，系统解析岗位、基于你的固定资料生成一份针对性简历，并给出「哪条要求有据可依、哪条只能按能力表述」的覆盖清单。

01一句话定位

一个 chat = 一个求职场景 = 恰好一份简历

层选型
后端FastAPI + SQLModel + SQLite(WAL) + asyncio 调度器
前端原生 ES Module（无构建工具），三视图 01 资料 / 02 工作区 / 03 简历
运行本机单进程，数据不出本机；无 API Key 自动进入 mock 降级模式，开箱即跑

04端到端数据流

从「粘贴 JD」到「产出简历」的主链路（对应 overview.md 的时序图）：

1 · 新建对话POST /api/chats → 对全局 Profile 做整体快照（profile_snapshot，profile_dirty=false）
2 · 贴 JDPOST /api/chats/{id}/messages {kind:"jd"} → 同步写 Chat.raw_text，广播 chat_message
3 · 生成前问答POST /api/chats/{id}/interview → 找「岗位需要但资料缺依据」的缺口，返回 questions[]
4 · 提交回答POST /api/chats/{id}/interview/submit {auto_generate:true} → 增量合并进快照（profile_dirty=true）→ enqueue
5 · 抢占scheduler：UPDATE chat SET status='running' WHERE id=? AND status='queued'（原子抢占）
6 · 生成run_chat：10% 载入快照 → 25% 解析岗位 → 60% 生成内容 → 85% 渲染 HTML → 100% 落库
7 · 完成WS chat_updated {status:"succeeded", resume_id} → 前端「查看简历 →」→ GET /api/resumes/{id}

07关键设计决策

D1 · 一个 chat = 一份简历（不做「一个 JD 一个任务」的批量模型）

为什么：批量模型下用户无法为某个岗位单独微调资料；chat 天然是「冻结的工作上下文」，持有自己的 profile_snapshot。

代价：不能一次并发产多份简历；调度器由旧 JobTask 机械重命名而来，100% 复用。

D2 · 模型输出 spec JSON 而非 HTML

为什么：① XSS 防线（autoescape 转义）；② 零 LLM 成本重排版（基于 spec 重渲染）；③ 样式一致、可编辑、可打印。

代价：必须严格遵守 SPEC_CONTRACT；_normalize_spec 要做大量字段兜底。

D3 · HTML 是简历唯一真相来源

为什么：用户会在工作台直接改 HTML，保存的也是 HTML；若以 spec 为真相，手改会在 re-render 时丢失。

代价：spec 与 html 可能不一致；「应用版式」是唯一允许分叉后重新对齐的入口。

D4 · Resume.chat_id 单向关联（删掉 Chat.resume_id）

为什么：双向引用会带来「删库绕外键」代码；单向关联下删 Chat 级联删 Resume，删 Resume 反向删 Chat，处理简单。

代价：列表每条 chat 多一次派生查询换取代码简单。

D5 · 重新生成 = 覆盖（但记 EditLog 以便回退）

为什么：一个 chat 恰好一份简历，不能堆 N 份；但用户可能后悔，留一条可回退历史。

代价：只保留「上一版」，不做完整版本树；重新生成会删除旧 EditLog。

08常见陷阱

  1. 别在 pipeline 里 import scheduler → 循环导入。取消检查用注入的 should_cancel 回调。
  2. chat_id ≠ resume_id：前者用于 chat.* 接口，后者用于 resume.* 接口，混用会 404。
  3. 进度会「倒退」：失败重试把 status 改回 queued 时必须同步把 progress 归零——这是刻意的。
  4. WebSocket 路径仍是 /ws/tasks，但事件名已改为 chat_*，按名字找路径会找不到。
  5. /api/tasks* 标了 deprecated 但有意保留：5 个 HTTP 级测试依赖它做安全网。

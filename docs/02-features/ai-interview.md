# 功能：AI 问答 / flashcard（生成前先问清楚）

> 这篇讲「为什么生成简历前要先问你几个问题」、两处入口的差别、flashcard 的交互细节、回答如何被增量整合，以及 Esc 与「跳过」的语义差别。
> 适合：使用者（尤其遇到「生成前补充资料」弹窗时）；要改问答逻辑/提示词的开发者。

实现：`backend/app/interview.py`、提示词 `backend/app/prompts.py`（`SYSTEM_INTERVIEW_QUESTIONS` / `SYSTEM_INTERVIEW_APPLY*`）、前端 `backend/app/static/js/interview.js`（弹窗交互）、两处入口分别在 `backend/app/routers/profile.py` 与 `backend/app/routers/chats.py`。

---

## 1. 为什么要在生成前问答

简历生成时会产出一份**匹配分析 / 覆盖清单**：岗位要求的每一条，都要在简历里有对应表述，且注明是「有据可依（grounded）」还是「能力层面（capability）」。

问题在于：用户资料与岗位之间**常常有缺口**——岗位要求 Kubernetes，你的资料里只有 Docker；岗位要求跨团队协作，你只写了「良好的沟通能力」。如果直接生成，模型只能把缺口写成泛泛的「能力层面」表述，匹配分析就会**缺依据**，简历说服力下降。

所以先问一轮：**找出「岗位需要、但资料缺依据」的点**，用具体问题引导你补充真实素材（而不是让你凭空编），补充后并入资料，再生成。

> 提示词对模型有明确约束：问题要贴着你的已有背景发散（资料偏后端、岗位偏前端 → 问你在前端方向有没有相关实践），并给出「没有也可以说没有，我们会如实处理」的出口。

## 2. 两处入口的差异

同一套机制，两种使用场景。

| | 资料页「让 AI 帮我完善」 | 工作区「生成前补充」 |
|---|---|---|
| 入口 | 按钮 `#btn-profile-ai` | 点「生成简历」后自动触发（有缺口才弹） |
| 接口 | `POST /api/profile/interview`（带可选 `focus`，前端当前传空） | `POST /api/chats/{id}/interview` |
| 找什么缺口 | **资料本身不够具体**之处（成果没量化、技能没深度、缺个人定位） | **岗位需要但资料缺依据**之处（逐条比对 `requirements`） |
| 分析输入 | 无岗位信息（提示词聚焦「把资料写得更专业」） | 该对话的岗位解析（`job_analysis`，未解析时先解析一次、不改 chat 状态） |
| 回答去向 | `POST /api/profile/interview/apply` → 写**全局资料** | `POST /api/chats/{id}/interview/submit` → 写**本对话快照**，并追加一条 `guidance` 消息 |
| 跳过按钮文案 | 「暂不需要」 | 「**跳过，直接生成**」 |
| 提交后 | 刷新资料表单，提示「已根据你的补充更新资料」 | 立即开始生成（`auto_generate=true`） |
| 前置条件 | 无（资料为空也能问定位类问题） | 需有岗位要求；资料为空时返回 400「尚未填写资料库…」 |

两处都受「正在生成中」限制：工作区在 `running`/`queued` 时返回 409「简历正在生成中，无法同时进行问答」。

## 3. flashcard 交互细节

弹窗 `#interview-dialog`，资料页与工作区共用同一个组件（`interview.js`）。

| 元素 | id | 行为 |
|---|---|---|
| 进度 | `#iv-progress` | 形如「第 1 / 3 张」 |
| 缺口清单 | `#iv-gaps` | 有缺口时展示「发现 N 处岗位要求在你的资料中暂无依据：…」（工作区场景常见） |
| 话题标签 | `#iv-topic` | 2-6 字，如「K8s 经验」 |
| 问题 / 提示 | `#iv-question` / `#iv-hint` | 问题正文 + 一句答题提示 |
| 回答框 | `#iv-answer` | 占位符来自卡片的 `placeholder`，缺省「写下你的回答（可留空）」 |
| 圆点导航 | `#iv-dots` | 每张一个圆点：已作答为 `is-done`，当前为 `is-current`；**点击圆点直接跳卡**；带 `aria-label` |
| 上一张 / 下一张 | `#iv-prev` / `#iv-next` | 到边界自动禁用 |
| 跳过这张 | `#iv-skip-card` | 清空当前卡回答并前进（最后一张则只清空） |
| 跳过全部 | `#iv-skip-all` | 文案由调用方给：工作区「跳过，直接生成」/ 资料页「暂不需要」 |
| 确认提交 | `#iv-submit` | 提交已填写的回答；提交中禁用并显示「提交中…」 |

要点：

- **切卡不丢答案**：回答存在组件状态 `st.answers[]` 里，来回切卡内容保留，圆点即时反映「已作答」。
- **支持只填部分**：`collect()` 只回传填了内容的回答；全空即等同「跳过全部」。也可以留空跳过某张卡，不会强制你回答。
- 最多 6 张（`interview.MAX_QUESTIONS`），按重要性排序；没有问题就不弹（`openInterview` 收到空数组直接返回）。
- 弹窗打开后焦点自动进入回答框；提交失败时弹窗**保持打开**便于重试或改点跳过；提交成功即关闭。

## 4. Esc = 取消（不生成）vs「跳过，直接生成」

这是最容易混的一点，两者语义**不可混用**：

| 操作 | 结果 | 是否生成 |
|---|---|---|
| **Esc**（或点击对话框关闭） | 触发 `onCancel`：工作区恢复按钮并提示「已取消补充，未开始生成。」然后**什么都不做** | **不生成** |
| **「跳过，直接生成」按钮**（`#iv-skip-all`） | 触发 `onSkip`：提交空回答并带 `auto_generate=true` | **立即生成** |

- 在 `interview.js` 里，`dialog` 的 `cancel` 事件被拦截（`ev.preventDefault()`）后走 `onCancel`，**绝不提交、绝不生成**。
- 「跳过，直接生成」是一个**独立的显式按钮**（`#iv-skip-all`），文案由调用方通过 `skipLabel` 注入，代表「我知道有缺口，但先不等了，直接生成」。
- 资料页的 Esc /「暂不需要」都是**只关闭、不发请求**（`onSkip`/`onCancel` 均为空函数）。

> 结论：Esc = 放弃这次生成（可稍后再点「生成简历」）；「跳过，直接生成」= 现在就生成。二者不是同一个「退出」。

## 5. 回答整合：增量契约（重点）

用户回答后，由 `POST …/interview/submit`（或 `…/interview/apply`）调用 `interview.apply_answers()`，把口语化回答提炼成专业表述并合并进资料。

**契约：模型只返回增量，不返回整份 profile。**

```json
{
  "summary_append":  "追加到个人概述的一段话（没有则空串）",
  "achievements":    [{ "exp_index": 0, "text": "一段专业表述" }],
  "skill_notes":     [{ "name": "已有技能名", "note": "一句话说明用途与程度" }],
  "projects_append": [{ "name": "项目名", "summary": "一句话", "highlights": ["要点"] }]
}
```

### 为什么不用「输出整份 profile」

早期版本让模型把**整份资料 JSON** 重新输出一遍。资料一多，输出 token 量爆炸，实测严重超时：代码注释记录「资料一大就要 90s+ 才返回」，本次回归实测更差（**200s+ 级**）。改为**只输出新增片段**后输出量骤降，延迟回到 **5 秒级**（代码注释记「10s 量级」，本次实测 **5.1s**）。

代价是后端要自己负责「怎么合」，于是有了下面这套明确、可预测的合并规则。

### 合并规则（`interview._merge_delta`，只追加、不改写、不删除）

| 增量字段 | 合并行为 |
|---|---|
| `summary_append` | 非空且原文未包含时，追加到 `summary` 末尾（换行分隔） |
| `achievements[]` | 按 `exp_index` 指向**已有**经历：`exp_index` 越界 → **忽略**（绝不新建假经历）；文本去重后追加到该经历的 `achievements`，单条截断 400 字符 |
| `skill_notes[]` | `name` 必须与资料中**已存在**的技能名匹配（小写比对，去空格）；**只更新已存在的技能**、不新增技能名；且仅在该技能 `note` 为空时写入，单条截断 200 字符 |
| `projects_append[]` | 按 `name`（小写）去重后追加；`name`≤120、`summary`≤400、`highlights` 最多 6 条、每条≤300 字符 |

> 这些「硬规则」的共同目的：**增量可以少，但绝不能造**。用户没提到的公司/项目/技能不会被凭空加进来。

### 无 API Key 时的启发式降级

未配置 Key（或 LLM 调用失败）时，整条链路仍可用，只是没有语言润色：

- **找缺口**：资料页用 `_profile_gaps_heuristic`（成果没量化 / 技能没深度 / 缺个人定位等问题）；工作区用 `_chat_gaps_heuristic`（对 `requirements` 逐条做「关键词是否在资料里出现」的重合度判断，命中 0 即为缺口，话题标签「待补充经历」）。
- **整合回答**：`_apply_heuristic` 把回答**原样**作为要点追加到第一条工作经历的 `achievements`；若没有经历，则拼进 `summary`。不做润色，不编造。

## 常见陷阱

1. **按 Esc 后按钮恢复、但没有生成**——这是设计如此。想继续，重新点「生成简历」即可；不要以为 Esc 等于「跳过并生成」。
2. **同一个 JD 只问一次**：回答会被合并进本对话快照，缺口补上后就不再重复问。这是预期行为（可「恢复默认」重置快照或新建对话来重新触发）。
3. **「跳过」后缺口不会被补**：直接生成时，岗位要求里没有资料支撑的条目会在覆盖清单里标成 `capability`（能力层面）——这是如实呈现，不是 bug。
4. **资料为空时工作区问答会被拒**（400）：请先在资料页保存至少姓名 / 一段经历 / 一项技能。
5. **问答期间不要中途刷新页面**：回答存在前端内存里，刷新会丢失未提交的内容。
6. **资料页的问答写的是全局资料**（会影响之后新建的对话），而工作区的问答只写本对话快照——用错入口会「污染」总档案。

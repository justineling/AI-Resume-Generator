## ⚠️ 本轮踩的坑 / 方法论教训（重要）

### 1. 做精确字符串替换前必须核对**完整块边界**
我改 `data-model.md` 时以为 `Resume ||--o{ EditLog` 是 Mermaid 代码块的最后一行，
就在其后插入 ` ``` ` 闭合 + 说明段 —— **但实体定义（`Profile {}`、`Chat {}` 等）还在同一块内**，
结果把块截断（围栏数变奇数），实体定义跑到代码块外。
**修复**：把说明移到**整个代码块之后**。**教训**：替换前先 `sed -n 'a,bp'` 看清整块范围，
不要凭「看起来像最后一行」判断。全库围栏配对检查脚本：
统计 ` ``` ` 出现次数，奇数即为不配对。

### 2. flaky 测试比失败的测试更危险
工程师报告 `ux_check` PASS 49/0，我独立跑却是 `49/0 → 48/1 → 交替`。
**只跑一次不能证明测试稳定**；要求「连跑 5 次全绿」才算修好。

**根因（用 value-setter 拦截 + 调用栈定位）**：
```
#ws-title-input ← ''  @ chat.js:241 fillComposer()  ← chat.js:224 openChat()
```
`newChat()` 的 `await api.createChat({})` 期间 UI **可交互**，网络稍慢时用户打的字
会被 `openChat` 回来的 `fillComposer(c)` 用空值覆盖吞掉。
**这不只是测试问题，是真实 UX 缺陷** —— 测试改同步点（等 `#ws-code` 变化）只是让断言变绿，
产品代码必须同时修（`creatingChat` 标志 + 不覆盖用户已输入内容）。

**教训**：测试 flaky 时，先判断「是测试同步问题还是产品竞态问题」，
**不要只改测试等待** —— 那会掩盖真实缺陷。

### 4. 对比度计算涉及 `opacity` 必须算**复合值**
工程师报 disabled 态 dark 2.40 / light 3.79，**漏算了 `.btn:disabled { opacity: 0.38 }`**。
正确顺序：① 文字(带 alpha) 先叠按钮底色 → ② 整个元素再按 opacity 叠页面底色。
我实测真实值：**dark 1.32 / light 1.52**。
**结论**：disabled 态**不修** —— WCAG 2.1 SC 1.4.3 明文豁免 inactive 控件；
低对比本就是「不可点」的视觉信号，强行拉到 4.5 会让禁用按钮看起来可点；
用户需要的信息由旁边状态文案承担（`"岗位要求为空：生成前请先粘贴 JD。"`，全对比度）。

## QA 独立抽检结论（有价值的验证范式）

避免 QA 变成逐条确认「代码存在」的橡皮图章。

## ⚠️ 本轮踩的坑 / 方法论教训（重要）

### 1. 做精确字符串替换前必须核对**完整块边界**
我改 `data-model.md` 时以为 `Resume ||--o{ EditLog` 是 Mermaid 代码块的最后一行，
就在其后插入 ` ``` ` 闭合 + 说明段 —— **但实体定义（`Profile {}`、`Chat {}` 等）还在同一块内**，
结果把块截断（围栏数变奇数），实体定义跑到代码块外。
**修复**：把说明移到**整个代码块之后**。**教训**：替换前先 `sed -n 'a,bp'` 看清整块范围，
不要凭「看起来像最后一行」判断。全库围栏配对检查脚本：
统计 ` ``` ` 出现次数，奇数即为不配对。

### 2. flaky 测试比失败的测试更危险
工程师报告 `ux_check` PASS 49/0，我独立跑却是 `49/0 → 48/1 → 交替`。
**只跑一次不能证明测试稳定**；要求「连跑 5 次全绿」才算修好。

**根因（用 value-setter 拦截 + 调用栈定位）**：
```
#ws-title-input ← ''  @ chat.js:241 fillComposer()  ← chat.js:224 openChat()
```
`newChat()` 的 `await api.createChat({})` 期间 UI **可交互**，网络稍慢时用户打的字
会被 `openChat` 回来的 `fillComposer(c)` 用空值覆盖吞掉。
**这不只是测试问题，是真实 UX 缺陷** —— 测试改同步点（等 `#ws-code` 变化）只是让断言变绿，
产品代码必须同时修（`creatingChat` 标志 + 不覆盖用户已输入内容）。

**教训**：测试 flaky 时，先判断「是测试同步问题还是产品竞态问题」，
**不要只改测试等待** —— 那会掩盖真实缺陷。

### 4. 对比度计算涉及 `opacity` 必须算**复合值**
工程师报 disabled 态 dark 2.40 / light 3.79，**漏算了 `.btn:disabled { opacity: 0.38 }`**。
正确顺序：① 文字(带 alpha) 先叠按钮底色 → ② 整个元素再按 opacity 叠页面底色。
我实测真实值：**dark 1.32 / light 1.52**。
**结论**：disabled 态**不修** —— WCAG 2.1 SC 1.4.3 明文豁免 inactive 控件；
低对比本就是「不可点」的视觉信号，强行拉到 4.5 会让禁用按钮看起来可点；
用户需要的信息由旁边状态文案承担（`"岗位要求为空：生成前请先粘贴 JD。"`，全对比度）。

## 收尾：我的 snippet 被工程师正确反驳（值得记下）

我给工程师的竞态修复代码**有两处缺陷**，它没照抄而是指出了问题 —— 这是好事：

1. **我写的 `creatingChat && (title.value || req.value)` 有缺陷**：无法区分「用户在新窗口里打的字」
   和「上一个对话残留的 composer 内容」。后者在真实场景里普遍存在（用户从上个对话点「新建」时，
   输入框还显示着上个对话的标题/JD）→ 会误判成「用户已输入」→ **新对话保留旧内容**
   （更糟：点生成会把旧 JD 存进新对话）。
   **正确做法**：在 `newChat()` 里、`await createChat` **之前同步清空** composer（含基准值），
   这样 `creatingChat` 窗口内「DOM 非空」就精确等价于「用户已开始输入」。
2. **我把 `savedTitle/savedReq` 的赋值放在了 `composerDirty()` 之前** —— 会让 `composerDirty()`
   拿新基准去比，改变「静默刷新不覆盖正在编辑内容」的既有语义。
   **正确做法**：先 `const dirty = composerDirty();`（用旧基准）再更新基准。

**教训**：给 worker 写「精确改法」时，**我自己也要考虑边界情形** ——
「用户在上个状态遗留的 DOM 值」这类**状态残留**是很容易漏的坑。

## 收尾：xss_probe 的 Windows 文件锁（测试隔离的最后一处）

全量跑测试时 `xss_probe` 报 `PermissionError: [WinError 32] ... being used by another process`。
根因两个：
1. `xss_probe.py` 是**最后一个自己写服务起停 + 清理**的脚本，用**裸 `unlink()`** 无 try/except
   —— Windows 上文件句柄释放有延迟，遇到瞬时锁直接崩（且崩在入口，连断言都跑不到）。
2. 它是 5 个 UI 脚本里唯一没改用共享 helper 的。

**修法**：改用 `_ui_server.spawn_isolated_server` / `stop_isolated_server`
（内含端口空闲检查 + try/except 清理 + terminate/wait），并删除随之失效的 `_wait_server`。
隔离库名也随之变为 `data/_ui_xss_probe.db`（原 `data/xss_probe.db`），已同步 `suite.md`。

**教训**：**同一个模式在 N 处重复实现时，迟早有一处漏掉健壮性**。
新脚本一律复用 `_ui_server`，不要各写各的。
